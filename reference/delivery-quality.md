# 需求、上下文与页面验收

本文件是新 RQ 的交付流程。使用项目现有文档/用例结构即可，不重复创建同义文档。
语义锚点或稳定用例 ID 均可；不得违反项目不使用数字需求编号等规范。
本文件的页面要求适用于有页面入口的需求；纯接口/CLI 用真实入口操作、响应与副作用证据替代，
覆盖门槛不变。有页面但环境不可用仍是 blocked。

## 1. 先保存事实，再拆任务

在协调目录或项目任务目录保存三项持久化资产，任务卡引用 worker 可读取的绝对路径或仓库相对路径：

- **需求与方案**：原始需求/追加消息的必要原文、附件路径及版本；逐项行为、数值、单位、默认值、
  禁止行为、边界和明确不做项；方案、契约、决策理由与尚未解决的问题。不可只留下主端改写的摘要。
- **用户用例**：按下文格式记录操作和预期；每条需求（包括同一句里的子要求）都有用例和开发负责人。
- **状态索引**（建议 `<coord>/state.md`）：当前阶段、上述资产位置/版本、真实会话 ID、attempt、
  卡片/契约版本、已合入 SHA、验收基线、失败/阻塞、未决决策和下一步。链接证据，不粘贴完整日志。

理解需求和确定方案后生成用例，完成上述覆盖核对才派实现卡。可先派只读探查/契约设计；
不能用“后续 verify 会补”跳过用例。发现新分支时补充用例并通知受影响 worker。
用户追加/纠正需求时更新来源、方案和用例，保留变更原因；不要通过修改预期适配错误实现。

### 可选参考资料（仅本次任务提供或指定时）

是否存在参考资料由本次任务决定。未提供或指定时，直接依据需求与项目现状工作，无需寻找、索取
demo，也不将其缺失视为阻塞。以下规则仅适用于任务提供或指定了 demo、原型或截图的情况。

用户提供 demo/原型/截图时，实际打开查看；可运行 demo 还须操作相关页面与状态。静态截图未展示
的行为按需求核对，缺失部分记录未知。仅搜索文件名或读 HTML 文本
不足以完成视觉与交互核对。先按用户路径、项目记录定位；缺资料如实记录，不能凭印象补齐。
保存稳定副本或原路径+版本，使开发与验收者访问同一份。
建立对照：`demo 页面/区域/状态 → 字段/布局/交互/业务口径 → 本次保留或变更 → 用例 → 负责人`。
用户明确的新要求覆盖 demo 的旧行为，记录差异；未明确的实质冲突先提出，不擅自选一个。
使用这些参考资料的任务卡应给出具体参考区域和状态，不能只写“参考 demo”。验收者独立对照实际页面与 demo，
覆盖列表、详情、弹窗、空态、错误态等本次相关状态；视觉要求以截图或实际查看结果佐证。

## 2. 用业务结果控制粒度

默认按既有模块组织，但“一个模块”并不代表工作量适中。每卡应能说明业务结果、拥有的文件、
契约和用例；一个共享文件/接口必须有唯一写入负责人。

- **过大**：含多个可独立验收的业务结果，或同时要求陌生领域探索、迁移、状态机、多个 UI 流程。
  按结果/依赖阶段拆开；同一模块可多卡，同一并行阶段写入范围不重叠。顺序阶段可交接同一文件，
  标明前置合入 SHA 和当前唯一负责人。不要把全部测试和最后接线留给主端。
- **过小**：只改一列/一个调用，却要等待另一卡、共享同批文件、无法独立验证。
  优先合入相关结果卡，或先后执行；有充分理由时允许小范围跨模块纵向卡，显式列出全部范围和依赖。
  不因模块编号不同强拆紧耦合的小改动，也不因此授权跨模块重构。
- **有依赖**：契约稳定后并行；实现探索决定契约时先做提供方；按 contract-first.md 选择。
  不以 worker 数量衡量并行效果。先验证一条最小真实主流程，再扩大并行批次。
- **完整流程**：指定一名端到端流程负责人，覆盖入口、跨模块状态流转、结果展示和失败恢复。
  可以由相关开发 worker 兼任协调责任，但不扩大其写入范围；独立 verify 验收整个流程。
- **回修**：按失败用例回派原负责人；出现重复同类返工时重新核对范围、契约和环境，必要时新开
  有完整资产引用的 fix 卡，不持续堆聊天补丁。一个较小任务可由同一个独立 worker 兼任 integ/verify。

派发前主端检查共用前缀、文件归属表和卡片范围一致。真实冲突先解决，不让 worker 猜优先级。
已有用户授权内的技术选择由主端裁定；需要用户决定的业务语义不可擅改。

## 3. 控制主端负担，压缩后可恢复

主端主要维护业务清单、决策和状态，环境修复、测试基础设施修复、实现回修分配有界 worker。
允许主端读必要 diff 和抽查页面；不把所有实现文件、完整日志和每次轮询结果反复灌入上下文。
探查报告只提交结论、来源位置、未知项及对拆分的影响。状态以增量读取，失败时才读取对应日志段。

在派发、需求/契约变更、收回执、回修、验收切换时更新状态索引，不等压缩提醒。
主端/worker 压缩或接手后，先读索引→本卡→相关原始需求及本次参考资料（如有）→用例/契约→最新回执与 Git 状态，
再继续动作。不能把聊天压缩摘要当成唯一需求来源；不能仅凭旧 summary/旧 attempt 宣称完成。
worker 报告已实现/未实现用例、决策、测试资产和当前提交，使换 session 无需复制全部历史。

派发前核实页面服务能从 worktree 启动、测试账号/种子可用、端口和数据库隔离、ORM 客户端与
本工作树 schema 一致。部分工具拒绝 `.git/` 下的页面资产，遇到时按项目已有流程使用可服务路径，
通过受支持的 worktree/绑定流程同步真实路径；不要手改名册掩盖不一致。共享测试数据无法隔离时串行持锁。
环境问题交给环境修复卡，避免每个业务 worker 独立重复修复。

## 4. 用户用例格式与覆盖

每条用例包含：来源锚点、业务目的、前置数据/身份/状态、**逐步页面操作**、每步可见预期、
最终业务状态/副作用、开发负责人、验收者、执行状态与证据。核心流程标识为必过。
业务分支先按角色/状态/数据条件/结果列决策表，再映射用例；覆盖本次需求可达且相关的所有分支，
没有实际关联的条件可写不适用及理由，不制造无限组合。不得用“异常已覆盖”替代具体条件。

- 核心流程用一套连续数据，从用户入口创建/选择到提交、下游处理和最终可见结果；不得用预置最终
  状态跳过被修改的步骤。相关默认值、筛选排序、边界、空数据、必填/非法输入、权限均列明。
- 有写入：重复点击、刷新重试、重复消息/请求、失败重试；核对只产生一次有效结果、无重复副作用。
- 有事务/异步/批处理：适用的中途失败、部分成功、超时未知、回滚或补偿、重试恢复、取消/撤回、
  并发冲突与留痕。先写清业务不变量（数量守恒、状态一致等）及提交边界，再设计能观察它的用例。
- 导入、下载、打印等通过页面触发，还要检查实际产物/预览内容，不能只断言按钮存在或请求成功。

例如“创建后留在原页，显示已建车次和剩余量”：用例必须连续创建两次，检查不跳页、两条车次、
剩余量更新和重复提交行为；只检查首次创建接口 200 不算覆盖。

## 5. 页面验收与闭环

确无页面入口的纯接口/CLI 需求，以真实 API/CLI 操作替代本节的页面步骤，记录不适用理由，
仍遵守完整流程、分支、失败证据与最终基线要求；有页面但当前打不开不属于此例外。
独立验收者从原始需求和用例出发，结合本次参考资料（如有），先查漏项，不能只照开发者列的成功测试验收。
在包含全部改动的集成版本启动真实前后端，记录 commit SHA、启动配置/开关、环境、身份和测试数据。
可用可用的浏览器工具或 Playwright 等驱动**实际 UI**；不要求特定工具。API/数据库只用于准备非被测
前置数据、受控故障注入和核对副作用，不能代替正在验证的用户操作。

先完整跑通核心主流程，再逐条跑所有适用用例（分支/异常/幂等/事务）。外部服务可按授权使用可控
测试替身，但明确边界；不得 mock 自己系统的业务 API 后声称前后端集成通过。回滚/并发语义还须
API/数据库/日志证据补充；页面触发、可见反馈和最终状态仍需验证。无法触发或观测时记 blocked，
说明缺少的测试能力，不能标 passed。真实外部环境检查遵守用户授权。

逐例记录：`来源/用例 → 实际操作 → 实际结果 → passed/failed/blocked/not-run → 截图/trace/报告路径
→ 基线 SHA/环境 → 缺陷与回修卡`。截图与日志脱敏；有运行日志才算执行，不以测试文件存在当证据。
一个用例多项断言任一失败，该例失败；失败必须保留在回执 tests 中，result=failed 或 blocked，
不要为绕过机械 done 校验移到 risks、改成 not-run 或删除失败断言。报告执行完毕不等于验收通过。

主端最终逐项核对需求→用例→页面证据，检查必过主流程与所有适用分支无漏项。失败回派修复，
复测失败项、受影响场景和完整主流程。代码或配置再次变更后记录证据失效范围并复测；最终交付说明
通过/失败/阻塞/未执行数、验收版本、证据位置。只有必需项全部通过才称需求完成。
