# 交付与长任务

## 持久事实与唯一当前快照

沿用项目已有文档结构，保存三类资产：

- 原始需求、追加/纠正原文与附件版本，方案/契约、决定理由及未知项；不只存模型改写的摘要。
- 用户用例：每条要求映射业务行为、负责人、验收者、操作/预期与证据；遵守项目锚点规范，不强造 L1/L2。
- CURRENT.md：唯一当前快照，链接上述资产，列阶段/依赖、真实 agent/attempt 与 runtime/capacity 证据、集成 SHA、验收 SHA、
  当前卡/验收约定版本及审定状态、当前失败与未决输入、下一步。用 snapshot 整体替换，旧快照自动归档，禁止并列多版“覆盖以上/下方”。

每次派发、收回执、需求/契约变更、回修和阶段切换更新快照。待处理问题按真实身份+turn/request ID 去重，
缺 ID 则按原问题指纹；保留原问题/来源、影响、首次时间、处理人、open/answered/resolved 和答案证据。
answered 只是已答，真实恢复后才 resolved；不要把普通进度/超时生成重复问题。
压缩/接手后：CURRENT→本卡→相关原始要求/资料→用例/契约→最新回执与 Git，随后按真实 native 状态推进全部任务。
中途重新加载/升级技能时，对照新规则复核当前执行表、依赖和生效任务卡；只重读技能不会自动改写旧计划。
保留有效成果与正在执行的现场，将受影响旧计划标为待替换；活跃任务按安全停点交接，结束后以完整新卡接续。
没有受到变化影响的任务继续，不重跑已有有效验证；不把重新建主会话当作修正计划的必需步骤。

## 最小共享背景与阅读地图

沿用现有项目资产：最小背景记录整体目标/边界；事实、契约、决定和失败尝试各有版本、证据、适用范围与未知项。
事实整理确需实际调查时按需委派一个唯一维护者，不设常驻资料岗位。稳定事实供其它卡引用，避免各 worker 重复摸底。
每卡列精准入口/相关文件、阅读顺序与目的、需读锚点/版本，区分必读和有具体问题再读的资料。
不复制整个共享背景、全量代码或历史；新结论更新版本并通知受影响卡，过期判断标失效，不能让每个 worker 自行重查同一事实。

## 唯一生效任务卡

每个任务以 `<module>.task.md` 为唯一完整生效卡，保存版本与内容哈希；生成的 prompt 只是该卡及执行协议的投递副本。
变更时主端汇总所有仍生效的要求、用户原文锚点、用例、契约和完成条件，整体替换当前卡；旧卡按 attempt 归档。
禁止“沿用v7，另读v10/v13，以下覆盖以上”式继承。原始资料可引用，不要求执行者从历史任务卡推导当前要求。
每轮续聊可以只补运行步骤，但不能在聊天补丁中改目标、范围、验收条件或权限；这类变化先更新完整卡和验收约定。
活跃任务不静默换卡：先通知受影响负责人，在安全停点结束本轮，再用 reply --task 发完整卡并确认新版本。
停点通知仅要求保存现场并结束本轮，不授权执行尚未派发的新要求。
紧急纠错或解除本任务阻塞可同 attempt 告知，不能夹带独立新工作；发送结果不确定时先核实，不重复派发。

## 结果负责与主端边界

主端维护目标、任务关系、共享资源和决策；完整结果由 worker 负责。环境探查、配置恢复、长异步运行、
集成打包与验收也应有结果负责人，不默认回流主端。角色按需要组合，不为每项工作固定增设岗位或管理层。
负责人在授权范围内推进定位→处理→自测→交接，验收失败后承接相关回修；独立验收者不替实现者改业务代码。
只读卡确实只交调查结论时，写明后续处理负责人；不能把“审计已完成”当整体问题已解决。
缺权限/输入时，交付已核事实、可行选项、推荐及最小必需操作。委派不扩大授权，不能代用户审批。
上报以状态、结论、成果版本、证据索引、剩余阻塞和需裁定事项为主；原始日志留产物目录，按需展开。

## 真实探路与扩大

长异步流程、外部研究、批量模型调用或跨模块未知较大时，在批量扩张前先做最小真实纵向试跑。
选能暴露关键风险的少量真实对象，贯通入口、实际执行、最终产物和业务判断；记录输入体量、真实终态、
失败与关键缺证。结构校验、accepted、固定响应、零实际研究不能作为业务成功。
出现输入过大、结果空缺、外部证据未取到或核心判断未执行时，先修链路，再扩大相同风险路径。
不依赖此结果的工作照常并行；同一个开发卡可先试跑再扩张，无需机械增加多张探路卡。
最终仍按用户完整数量、数据和用例验收，明确小样本覆盖哪些项、哪些尚未执行，不能缩减最终范围。

## 执行者接续

主端不加载全部源码和完整日志；worker 提交结论、来源、证据链接与未知项。
先 collect 精简回执并收存同 attempt handoff，配合 native 终态；异常/缺回执/证据矛盾才定向展开必要证据。

`module` 是结果任务的唯一身份，角色或专业领域可以相同，不能把一个岗位永久绑定一个线程。先作如下判断：

| 情况 | 动作 |
|---|---|
| 新结果可独立验收，不依赖旧执行者现场 | 新 module prepare、新原生子智能体；不论旧任务是否结束 |
| 同一结果的紧密关联修复/接续，保留上下文最有效 | 旧执行轮终态后 reuse，写具体 reuse-reason |
| 同一结果需接手旧资产，旧假设/上下文或能力障碍使换人更有效 | 旧执行轮终态后 fresh，保留任务身份和资产 |
| 原任务仍运行，只需补必要答案/解除阻塞 | 同 attempt 消息，只承接当前任务，不排新任务 |

比如安装联调尚未完成，又要独立核查另一实例的搜索能力：新建同专业的搜索任务，不能因都属 runtime 而续聊安装线程。
紧密关联以共享未完成结果、同一缺陷链和有价值的执行现场为依据；只是同目录、同角色或闲置线程都不够。
新任务若写入重叠文件，先分清唯一写入负责人或建立依赖，不能借换线程绕过冲突；只读调查可独立并行。

reuse 与 fresh 都先确认目标旧执行轮的真实终态；业务回执/名册不能代替 `wait_agent` 证据。
关联缺陷优先保留现场，不能仅按时间、轮数或阶段名称 fresh；同岗位或闲置 agent 也不构成关联理由。

1. reuse 给具体效果/速度理由，用同 agent 的 send_input 保留自身历史；fork_context 只用于新建，不是每轮清空。
2. fresh 给实际换人收益，收存同 attempt handoff、需求/用例/契约版本、事实/失败尝试、原资产路径、SHA及未提交内容。
   身份与继承分开判断：新建默认显式 false；主历史短且聚焦、任务高度相关且转述遗漏风险/整理成本明显更高时，PM 可 true 并用 register --context-reason 记一句理由，不问用户。
   true 只复制主端当前历史；不按阶段机械禁 fresh true，但噪声多、清除旧假设的诊断/fresh 和独立验收执行用 false。author 准备资产可按收益选择，继承过主历史则 execute 前 fresh false。
   继承不替代完整任务卡、完成条件、写入范围及旧 worker 交接；需要旧 worker 自身现场时优先 reuse。
3. 本地 reply 生成新 attempt，主端实际 send 或 spawn 后登记真实证据。fresh 保持 module/原树/成果与旧身份链，旧者仍写就不能接管。
   failed/blocked 且之前未能持久 bind 的真实树也必须核验收存；不能因为名册 worktree=null 就另建树丢现场。
4. 结果与交接保存后及时 close 释放容量，previous_status 只是旧快照；已确认旧轮结束并成功 close 才记关闭/释放，后续 not_found 不撤销此证明；孤立 not_found 仍未知。
   已关闭 reuse 按实际 resume 能力核同身份恢复；not_found 不是完成或停止证明，也不保证跨重启恢复。

具体参数和状态见 [原生操作](native-codex.md)。CLI 不能证明证据来自真实宿主；主端负责真实调用与观察，脚本不代调 native tools。
反复回修需重审原始要求、契约、环境和失败尝试；原有三轮复核护栏仍可 `--force` 后继续 reuse，不把次数当强制 fresh。
主端交接只保留 CURRENT 与资产索引，不默认创建另一个用户会话。

## 验收与测试分工

派实现前生成用例，每条含来源、目的、前置身份/数据、逐步操作与可见预期、最终状态/副作用、负责人和证据。
每轮实现者提出可交付行为与验证方式，独立 evaluator/verify 对照原始要求审定，写进当前任务卡/引用的同版验收约定后开工。
审定只需把真实入口、成功与失败条件、证据和范围定清；按可独立结果放行，不等全项目设计/全部自动化脚本完成，
也不为小回修重新设计整套验收。某块存在未审定条件，只阻塞它及真正受影响的路径。
沿用未变条件可直接确认版本；要求变化只重审受影响部分。实现与验收的意见分歧由主端裁定，不放宽用户要求换取一致。
核心流程用连续数据从入口跑到最终结果；分支按角色/状态/条件列决策表，覆盖相关默认值、边界、权限与异常。
写入验证重复点击/重试/刷新/消息幂等；事务/异步验证部分失败、超时未知、恢复/补偿、取消及适用并发不变量。
导入/下载/打印还要核实际产物内容，不止检查按钮或请求成功。

验证分三层，执行表和任务卡写明每层由谁做、哪些前置就绪、什么证据可以放行：

1. **模块定向验证**：独立服务/决策点先验证自身正反例、相关边界与失败路径，绑定实现SHA。
   上游未就绪时可用冻结契约的替身隔离自测，明确标作契约测试，不能计真实融合或最终通过。
2. **局部真实融合**：提供方与消费方相关路径定向验证通过后，使用真实实现贯通实际入口和结果，验证字段语义、
   引用/单位/缺失与错误传播、相关状态及副作用；如取数→某决策点。不依赖其它模块就不等待全体完成。
   可增量合入已通过改动并在包含双方改动的SHA验证；失败只阻塞受影响路径，返回对应负责人修复。
3. **完整集成与交付**：必需局部链路通过并合入后，统一跑完整主流程、跨模块回归、实际安装包/页面与最终业务产物。
   前两层不能抵扣最终必需范围；保留局部证据，不把最终集成当首次发现接线/业务问题的场所。

开发各跑相关最小自测，E2E 默认≤6 spec且≤15分钟。该预算不是模块/会话数上限。超预算交统一回归，不各自扩全量。
集成/回归负责人在全部相关合入后，用 e2e-scope plan 合成已登记范围与集成 diff，去重后统一执行一次；主端只协调与放行。
公共 schema/迁移/seed、共享基座/鉴权/全局配置、跨≥3模块的数据流，或项目发布规范要求时升级全量并记录理由。
verify/regression 只有紧密关联、复用更有效时才由同一独立 worker 分阶段承担，不因岗位相似自动复用。
author 先审定完成条件，再并行准备脚本缩短尾部等待。
author→execute 若当前卡已完整约定两阶段范围和切换条件，可仅切 phase；否则同时用 --task 发完整执行卡，不能以阶段参数覆盖卡片。
环境修复集中交给明确负责人，避免各 worker 重复修。共享数据/生成客户端无法隔离时持锁串行。

独立验收在最终集成 SHA 启动真实服务；有页面就实际操作页面，不 mock 自家业务 API 充当集成通过。
API/数据库可准备非被测前置数据、注入受控故障及核副作用。确无页面的 CLI/研究需求说明原因，验证实际入口；
有页面但不可用是 blocked。给定 demo/原型须实际查看对应区域与状态，未经指定不强行索取 demo。

逐例记录：来源/用例→实际操作→结果→passed/failed/blocked/not-run→脱敏截图/trace/报告→SHA/环境→缺陷负责人。
当前失败如实保留，不能改预期、删断言或移到 risks 取得 done。修复前失败存 resolved_failures，与当前未解决失败分开。
只改回执格式、补交接且代码/环境/基线不变时，重校协议即可，保留原有效证据；发生变化才按影响范围复测。
最终复测失败项、受影响分支及完整主流程；后续合入使证据过期时更新，不沿用旧 SHA 的“全部通过”。
最终报告覆盖数、失败/阻塞/未执行、验收版本和证据位置，所有必需项通过才称完成。
