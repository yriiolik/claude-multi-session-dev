# 跨模块契约与联调（v2）

本文件规定业务协作；派发/回执使用 v2-commands.md，不使用历史 cc-dispatch 命令。
粒度遵循 delivery-quality.md，不按模块数量或编号强制创建 session。

## 选择方式

已有稳定接口且本次不改语义：引用接口与测试即可，不额外派契约卡。
新增跨 worker 接口、共享 DTO/事件、共同写入数据或状态流转时，先明确契约再并行。

- **A 契约先行**：提供方先定契约，主端按原始需求和用例核对，定稿后提供方/消费方并行。
  消费方可 mock 对端自测；最终必须去掉内部业务 mock，独立联调和页面验收（有页面入口时）。
- **B 提供方先行**：契约依赖实现探索，或消费方接入很小，先实现提供方，再按真实接口接入。
  可把联调与独立页面验收（有页面入口时）交给同一个 worker；不能省略完整流程验证。
- **C 有界打样**：关键字段、事务或跨模块链路无法从文档确定时，派范围明确的 spike 卡验证
  最大未知项，产出契约、最小接线与检查证据。只有确有必要才加骨架/开关，不因跨三个模块自动打样。
  桩/固定值通过只能证明接线；真实业务链路在实现后必须重新验证。spike 若需合回文件用 developer
  角色并明确文件范围；不可把骨架测试绿当作需求完成。

同一 worker 可先产契约，主端复核后 reply 继续实现，避免为短步骤频繁新建会话。
主端可维护协调契约文档；复杂领域设计交给提供方，主端负责完整性、冲突与业务裁定。

## 契约需要明确的内容

按实际涉及内容写：接口签名、请求/响应 schema、必填/可空/默认值、数量单位、字段来源/去向、
错误语义、状态迁移、权限、事件和副作用、成功/失败示例。涉及写入还要明确：
幂等键作用域、重复/重试结果、事务提交边界、异步发送时机、部分成功与超时未知、回滚/补偿、
取消与并发顺序。逐项关联需求/用例；消费方每个必要字段都应有生产者，不能靠猜测补值。

所有参与者引用同一契约版本；变更时记录影响用例、通知提供方和消费方并重新核验。
公共 schema、迁移、路由注册和开关各有唯一写入负责人；归属表与任务卡不能相互矛盾。

## 集成验收

所有依赖合入后，从集成 SHA 启动真实服务。独立 integ/verify 先跑完整主流程，再验证每项用户用例，
包括适用的异常、幂等和事务。运行配置必须记录，尤其是功能开关与 mock 边界。
发现问题保留失败证据并回派修复；验收者不修改业务代码或放宽断言迎合实现。
完成规则与页面证据格式见 delivery-quality.md，模块 done 只代表交付待验收。
